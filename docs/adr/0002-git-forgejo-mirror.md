> **Project-description summary.** PaperOS keeps Git as its storage and wire format and buys independence at the forge layer, not the format layer. A self-hosted Forgejo on our own VPS is the source of truth for every repository; the GitHub organisation `imagine-os` is a mirror and the public front door, kept in step by per-repository push mirroring and a drift monitor. Forgejo Actions runners exist so CI survives a GitHub outage, and a recovery drill rebuilds the whole estate from Forgejo backups with GitHub offline. Building a version control system from scratch is rejected, and Jujutsu is allowed only as a personal client over a Git repository. This decision reopens on measured triggers, not opinion. (112 words)

## Context

PaperOS is built by up to twenty concurrent Claude sessions and one human. Every session takes one Linear issue, works in its own git worktree on a branch named after the issue, runs the CI gates, and integrates. Linear is the system of record for work; the forge is the system of record for code. Three questions had to be answered before any of the forge issues (PAP-45 through PAP-53) could start, and they are separable:

1. **What is the storage and wire format?** Git, or something else (Pijul's patch theory, a Jujutsu-native repository, a PaperOS-specific format).
2. **Which forge holds the source of truth?** GitHub, a self-hosted GitLab CE, a self-hosted Gitea, or a self-hosted Forgejo.
3. **Where does GitHub sit if it is not the source of truth?** Gone, read-only mirror, or a writable second primary.

The forces on the answer:

* **Agent tooling is Git-shaped.** Claude Code, the Claude Code Remote sandboxes, `worktree.sh` (PAP-46), lefthook and gitleaks pre-commit hooks (`r4/forge/push-protection`), commitlint, Renovate, release-please and every CI action in the estate speak `git` and the GitHub REST/GraphQL shape. Anything that breaks `git` breaks the build loop on day one.
* **The stated intent is independence from a vendor, not from a data format.** The Blueprint's decision line reads: "Do not build a VCS. […] The intent is independence from GitHub, not a new data format."
* **GitHub is a real dependency risk, but a measurable one.** Between May 2025 and April 2026 GitHub recorded 257 incidents, 48 of them major, totalling 112 h 18 min of downtime across major outages; February 2026 alone had 37 incidents and 7 major outages.[^gh-incidents] GitHub's own August 2026 availability report lists five further incidents of degraded service.[^gh-aug2026] None of those was a multi-day loss of git hosting, and the capture risk that matters to us is commercial and political, not availability.
* **The forge market has a documented capture precedent.** In October 2022 the Gitea trademarks and domains were transferred to the newly formed for-profit Gitea Ltd without community consultation; Codeberg e.V. forked Forgejo in December 2022 in reaction, and Forgejo made a full break from the Gitea codebase in early 2024.[^gitea-capture][^lwn-break] The lesson is that a permissive licence alone does not prevent capture — governance does.
* **Git itself is not frozen.** Git 2.29 (2020) added SHA-256 repositories, Git 2.48–2.51 landed reftable and SHA-256-by-default groundwork, and Git 3.0 is targeted at late 2026 with SHA-256 as the default hash; SHA-1↔SHA-256 interoperability and forge support (GitHub in particular) are the remaining blockers.[^git-transition][^lwn-git3] Choosing Git does not mean choosing a dead format, and it does mean tracking a format migration we do not control.
* **Budget and calendar.** The forge milestone "Forgejo live and mirrored" targets 2026-09-20 and the whole P0 foundation is measured in days, not months. A decision that costs more than a few engineer-days to implement is not affordable at this point in the plan.
* **Nobody is on call.** There is one human, and he does not review pull requests. Any self-hosted component has to survive with roughly an hour a week of attention, automated backups, and a rehearsed restore.

**Current state at the time of writing (important for anyone reading this in flight):** Forgejo is not deployed yet. PAP-45 deploys it, PAP-47 configures mirroring, and until then the build loop runs GitHub-only on `imagine-os` (see `docs/decisions/0001-build-pilot-operating-mode.md` in the plan repository). This ADR records the target topology and the direction of travel; PAP-47 is the issue that actually flips the source of truth.

## Decision

**D1 — Git stays the storage and wire format.** Every PaperOS repository is a Git repository. No custom version control system will be built. The commit graph, refs and pack format are treated as a public contract that tooling may depend on.

**D2 — A self-hosted Forgejo is the primary forge.** Forgejo is pinned to the current **LTS** major, `15.x` (v15.0 released 2026-04-16, LTS, supported until 2027-07-15).[^forgejo-eol] Standard (non-LTS) majors such as 16.x get three months of support and are not pinned in production.[^forgejo-eol] Upgrades follow the runbook in PAP-275 and move LTS to LTS.

**D3 — The GitHub organisation `imagine-os` is a mirror and the public front door, never the source of truth.** It keeps GitHub Pages demos, public discoverability, GitHub Actions capacity while it is free and working, and the integrations Justin already uses. If GitHub disappeared, PaperOS would lose reach and hosted CI minutes, not code or history.

**D4 — Mirroring topology: Forgejo is the write side; GitHub is a push-mirror target.** Each repository is a normal Forgejo repository with a GitHub push mirror configured to sync on push (Forgejo's push mirror force-pushes and overwrites the remote, so exactly one direction may be armed at a time).[^forgejo-mirror] GitHub receives writes only in the declared failover mode, and returning from failover is a scripted, one-way re-seed. The full topology, the failover procedure, the loop-safety marker and the failure modes live in [`docs/platform/forge-topology.md`](../platform/forge-topology.md); PAP-47 implements it and `r4/forge/mirror-drift-monitor` measures it.

**D5 — Forgejo Actions is the CI fallback, and workflow portability is a build requirement.** Forgejo Actions is explicitly "designed to be familiar to users of GitHub Actions, but […] not designed to be compatible": the default runner image is Debian bookworm with node.js rather than GitHub's `ubuntu` image, some `github` context keys are missing, `permissions` and `continue-on-error` job subkeys are ignored, and OIDC uses `enable-openid-connect` instead of `permissions: id-token: write`.[^forgejo-gha] Therefore portability is not assumed; it is checked by `check-workflow-portability.ts` (PAP-50, `r4/forge/portability-checker`) and proved by the disaster-recovery drill (PAP-53).

**D6 — A custom VCS is deferred indefinitely, and Jujutsu is permitted only as a personal client.** A contributor or agent may drive a PaperOS repository with `jj` over its Git backend, because that leaves the repository a Git repository. `jj` must not become the repository format, a required tool, or a CI dependency, because it does not support hooks, submodules, Git LFS, `git-worktree` or sparse checkouts,[^jj-gitcompat] and worktrees plus hooks are load-bearing in PAP-46 and `r4/forge/push-protection`.

**D7 — This decision is reopened by measurement, not by opinion.** The Reopen Criteria below are numeric, each has a named source of truth, and the release digest (PAP-88) quotes the checklist when a criterion trips.

**Criteria (each scored 1 = poor to 5 = excellent; the total out of 30 is a summary, not the decision rule).**

1. **Agent tooling compatibility** — does the whole agent toolchain (git CLI, worktrees, hooks, LFS, Renovate, release-please, Playwright CI actions, the GitHub-shaped API our `ForgePort` wraps) work unchanged?
2. **Self-host cost** — RAM, disk and ops hours per week to run it for ~20 concurrent agent sessions and ~30 repositories.
3. **Migration effort** — engineer-days from today's GitHub-only state to a working primary, including mirroring, bots and CI.
4. **Licence and governance** — the licence text *and* who controls the trademark, domains and roadmap.
5. **Vendor-capture risk** — how exposed we are to a unilateral change of terms, licence or ownership.
6. **Operational maturity** — release discipline, security response, backup and restore story, and how much of it we would be first to try.

**Why each rejected option was rejected.**

* **GitHub only** — scores well on everything we do not care about and worst on the only thing this project exists to fix. One supplier holds the code, the CI, the artefact registry, the identity and the public front door; the terms of all five can change without us. Kept as a mirror (D3) so we keep the upside without the exposure.
* **GitLab CE** — the most mature self-hosted option, and disqualified on cost and shape: a 16 GB baseline (8 GB floor)[^gitlab-req] against Forgejo's 2 GB is the difference between a €8.49/month Hetzner CX33 and something several times larger,[^hetzner] and open-core means the features we would grow into keep landing in the proprietary edition.
* **Gitea** — technically almost identical to Forgejo, and rejected purely on governance. The 2022 trademark and domain transfer to Gitea Ltd is precisely the capture event this ADR is trying to be robust against.[^gitea-capture]
* **Jujutsu** — genuinely better ergonomics for the rebase-heavy work agents do, and not adoptable as infrastructure: the missing features are exactly the ones our operating model rests on (worktree per issue, pre-commit hooks for secret scanning, LFS for screenshots and fixtures).[^jj-gitcompat] Permitted as a personal client under D6; revisit at 1.0 (see RC-6).
* **Pijul** — a better theory of patches than Git's, and a total loss of ecosystem. No agent tool, CI action, hosting platform or reviewer knows it. Not affordable, and the intent was never a new format.
* **From-scratch PaperOS VCS** — would consume the entire budget, produce a worse `git`, and break every tool agents rely on. Explicitly out of scope in the project Contract ("Non-goal: a from-scratch version control system; the ADR records why").

## Consequences

1. **Every repository exists twice, and drift is a monitored condition, not an assumption.** Forgejo holds the source of truth and push-mirrors to GitHub on every push. Divergence is detected hourly by `mirror-check.ts` comparing heads and tags on both forges, which files an issue through PAP-97 when they differ. Owner: PAP-47 and `r4/forge/mirror-drift-monitor`. Cost: one more moving part in every incident postmortem.
2. **Agents authenticate with per-character bot identities on both forges.** Each character gets a scoped Forgejo bot account and a GitHub App installation identity, with per-character commit identities, SSH signing keys, `.mailmap` and `allowed_signers`; tokens are short-lived and fetched through the credential broker rather than held in sessions. Owner: PAP-48 and `r4/forge/github-app-identities`, `r4/forge/git-credential-helper`. Cost: two access matrices to audit and rotate instead of one.
3. **CI is written twice-portable and proved on the fallback.** Workflows must run on both GitHub Actions and Forgejo Actions despite the documented incompatibilities,[^forgejo-gha] which means no GitHub-only actions without a vendored mirror, no reliance on ignored job keys, and a runner image that carries Playwright browsers so the visual gates are not GitHub-only. Owner: PAP-50, `r4/forge/portability-checker`, `r4/forge/playwright-runner-image`. Cost: the cheapest CI shortcut is usually the non-portable one, and the portability checker will keep saying no.
4. **We own an always-on service, its backups and its restore.** Forgejo behind Caddy with SSO, nightly restic backups, a timed restore drill and an upgrade runbook are now permanent obligations, budgeted at roughly one hour a week plus an LTS upgrade twice a year.[^ops-hours] Owner: PAP-45, PAP-273, PAP-274, PAP-275. Cost: a €8.49/month class VPS[^hetzner] and the first real on-call surface the project has.
5. **Forgejo Actions divergence is a standing tax on the CI estate.** Because Forgejo deliberately does not track GitHub Actions,[^forgejo-gha] every new GitHub feature the gates might use (merge queue, push protection, attestations) has to be re-implemented, approximated or dropped on the Forgejo side, and the disaster-recovery drill is the only thing that tells us which. Owner: PAP-53, `r4/forge/merge-automation`, `r4/forge/push-protection`.
6. **Git LFS is a split-brain risk we accept knowingly.** Forgejo's mirroring does not carry LFS objects over SSH,[^forgejo-mirror] so screenshots, videos and large fixtures need an explicit LFS strategy on both forges rather than "it mirrors like everything else". Owner: `r4/forge/lfs-and-artifacts`.
7. **A Git format migration is on the horizon and is not ours to schedule.** Git 3.0 with SHA-256 by default is targeted for late 2026 and forge support — GitHub's in particular — is the blocker.[^git-transition][^lwn-git3] Choosing Git means we inherit that migration; RC-7 below is how we notice it has arrived.
8. **Reversibility is cheap in one direction and expensive in the other.** Because the format stays Git, moving the primary back to GitHub, or on to a third forge, is a re-seed and a DNS change (the drill in PAP-53 rehearses the hard half). Moving off Git would have been irreversible. That asymmetry is the core of this decision.

## Reopen Criteria

Each criterion is numeric, has a source of truth and a named owner, and is evaluated at the monthly ops review; PAP-88's release digest quotes this checklist verbatim when one trips. Tripping a criterion opens a `Needs Justin` card with this ADR and the measurement attached — it does not by itself change the decision.

| ID | Criterion | Threshold (numeric) | Measured from | Owner | If it trips |
|---|---|---|---|---|---|
| RC-1 | Forge operations effort | Forge ops (patching, upgrades, incidents, backup babysitting, excluding feature work) exceeds **4.0 hours in any calendar month**, or **3.0 h/month averaged over 3 consecutive months** | Time logged against forge ops issues in Linear, monthly rollup | Forge | Re-score GitHub-only and managed-forge options; self-hosting was justified at ~1 h/week |
| RC-2 | Forgejo licence or governance change | Forgejo ships a release under a licence that is **not GPL-3.0-or-later** (or adds any non-free edition), **or** the trademark/domains leave Codeberg e.V. | `LICENSE` in the release tarball at each upgrade; Forgejo announcements | Forge | Evaluate the Forgejo fork landscape and Gitea; the Gitea precedent[^gitea-capture] is the playbook |
| RC-3 | GitHub unavailability | GitHub **git hosting** (push/fetch on `imagine-os`) is unavailable for a cumulative **> 24 h in any calendar quarter**, or a single incident **> 8 h** | GitHub availability reports[^gh-aug2026] plus our own mirror-monitor failure log | Forge | Downgrade GitHub from "front door" to "archive only"; stop depending on GitHub Actions minutes |
| RC-4 | Forgejo unavailability | Forgejo is unavailable **> 4 h in any calendar month**, or the restore drill's **RTO exceeds 2 h** or **RPO exceeds 24 h** twice in a row | Uptime checks (PAP-40, `r4/forge/forge-observability`) and DR drill `report.json` (PAP-53) | Forge | Re-open D2: managed Forgejo hosting, a second host, or GitHub-primary with Forgejo as mirror |
| RC-5 | Mirror drift | Mirror divergence between the two forges is detected on **> 2 occasions in any 30-day window**, or any single divergence takes **> 60 min** to reconcile | `mirror-status.json` from `r4/forge/mirror-drift-monitor` | Forge | Re-open D4: consider one-way archive mirroring instead of a live second forge |
| RC-6 | Jujutsu maturity | `jj` reaches **1.0** *and* supports **all four** of: hooks, `git-worktree`-equivalent multiple working copies, Git LFS, sparse checkouts | The jj release notes and Git-compatibility page[^jj-release][^jj-gitcompat] | Forge | Re-open D6 to allow `jj` as a supported (still not required) agent client with CI support |
| RC-7 | Git format limitation | A required PaperOS capability is blocked by the Git format for **> 14 days** with no workaround — concretely: any single repository exceeding **5 GB** or any file exceeding **100 MB** that LFS cannot absorb, a clone of any repository taking **> 5 min** on the CI runner, **or** both of our forges supporting SHA-256 repositories while a required tool does not | CI clone timings, repository size lint (`r4/forge/lfs-and-artifacts`), Git 3.0 / forge release notes[^git-transition][^lwn-git3] | Forge | Re-open D1 — in the first instance by adopting Git's own answers (partial clone, LFS, SHA-256 migration), and only then by re-examining a different format |
| RC-8 | Custom VCS | Any two of RC-1, RC-5 and RC-7 are tripped in the same quarter | This checklist | Atlas | Only then is a bespoke VCS re-examined, and only with a written cost model beating the 120-day estimate above |
